# Quarantine (P1B-13)

`harness quarantine sweep` is the never-delete half of cleanup: when a ticket ends, anything left in the ticket's roots that the manifest does NOT own is carried, whole and untouched, to a quarantine shelf — it might be somebody's real work. Deleting the things the manifest DOES own as scratch (`temp_dir` entries) is a second, separate, explicit verb that names exactly one id. The sweep itself never deletes anything.

A third verb, `harness quarantine drop-build`, deletes only cache-tagged build output of a ticket whose manifest shows it closed (section below).

A fourth verb, `harness quarantine put`, moves one item onto the shelf under `@shelf` with a label written before the move; it removes nothing (section below).

Code: `core/rust/harness/src/quarantine.rs` and `core/rust/harness/src/quarantine/put.rs` (Unix only), the verb dispatch in `core/rust/harness/src/cli.rs`. The roots come from the ticket's manifest (`docs/resource-manifest.md`), the workspace shape from `docs/workspace.md`, and the `quarantined` event from `docs/event-log.md`.

## `harness quarantine sweep`

```
harness quarantine sweep <ticket> --manifest-dir <abs> --workspace-root <abs> --quarantine-dir <abs>
    --log <abs> --repo <token> --role <token> --model <token> [--max-items <n>] [--ts-ms <n>]
```

- **Roots** = the `root` lines of the ticket's manifest, read through the manifest reader — never from a CLI argument, never guessed. A damaged manifest (missing, torn tail, corrupt) owns nothing, so the sweep refuses: exit 2, nothing moved.
- **Allowed base.** `--workspace-root` must be an existing, real (never a link), canonicalizable directory, not `/` — the same rules as `workspace create`. Every root must itself be a real directory checked with a no-follow stat (a root that IS a symlink → exit 2) and must resolve strictly inside `--workspace-root` (outside → exit 2). Every refusal fires before anything is written.
- **What a leftover is.** A top-down walk of each root using no-follow stats only. An entry a live path entry owns (equals or inside) is skipped whole; an entry a live path entry lies inside is descended into; anything else is a leftover and is moved as one unit (whole subtree, one rename). Stray files inside the worktree `tree` are NOT this verb's business — that is the clean-state check (P1B-11, ticket #155).
- **Symlinks are never followed.** A symlink in a root is a leftover like any other and is moved as the link itself; its target is never read, stat-followed or touched. The listed `node_modules` link is owned and therefore skipped.
- **Shelf layout.** `<quarantine-dir>/<ticket>/<batch>/<item>`: `<batch>` is a fresh token `b-<ts_ms>-<pid>-<seq>` minted with an EXCLUSIVE create (exists → next seq, never reused) at mode 0700, and `<item>` is `i-<n>` inside that fresh batch. Original names are never used as quarantine names (they may not be tokens or UTF-8). Nothing already on the shelf is ever renamed onto, replaced or removed; the item name is checked absent with a no-follow stat immediately before the rename. The shelf itself (`<quarantine-dir>/<ticket>`) is examined with a no-follow stat before it is read or made: a symlink or a regular file there is refused (exit 2) — otherwise every batch, journal and item would land outside the quarantine dir.
- **Ancestor re-check before each move (r2, F2).** The walk records, for every leftover, its ancestor chain — the root and each real directory between the root and the leftover — with the dev/ino each had when the walk examined it. Immediately before the item's rename (and before its journal line), every recorded ancestor is re-examined with a no-follow, NON-BLOCKING directory open (`O_DIRECTORY | O_NOFOLLOW`): it must still be the SAME real directory (same dev, same ino, never a link, never a FIFO or device — the open itself refuses those at once, so a swapped-in named pipe can never hang the sweep). An ancestor swapped for a symlink in the gap between the walk and the move — or swapped mid-run — makes the sweep SKIP that item: nothing moved for it, no journal line, no event, and the run ends exit 3 naming the item token (never a path). A narrow check-then-act window remains between this check and the rename itself; it is named under "v1 limits" below.
- **Write-ahead order per item.** (a) one intent line appended to `<batch>/journal.jsonl` under an exclusive lock, one write, `sync_all` — the item token, the source path relative to the workspace root as hex-encoded raw bytes, and the reason; (b) the rename; (c) the `quarantined` event through the library record writer (`reason` `unmanifested`, `to` = `<ticket>/<batch>/<item>`, `from` = the source relpath when every segment is a token, else `<ticket>/untokenable/<item>` — the journal holds the exact bytes either way). The event is written after the move because it states a move that happened; the journal line is the crash trace.
- **Idempotent re-run / crash recovery.** Before walking, the sweep reconciles every journal under the ticket's shelf. An intent that already has its matching event is settled (whatever sits at the source path now is a later leftover of the same name — the walk's business). An intent whose item is on the shelf and whose source is gone, with no event, gets its event written. An intent whose source still exists and whose item is absent is simply found again by the walk. An intent with no event whose source AND item both exist, or neither exists, cannot be decided: exit 3, nothing moved. A second sweep after a complete one moves nothing, writes no event, exits 0.
- **Event log placement.** `--log` must lie OUTSIDE every root (resolved through its nearest existing ancestor, so a not-yet-created log dir inside a root is refused too): a log written inside a root would itself be an unmanifested leftover the next sweep carries off. Inside a root → exit 2, nothing moved.
- **Cross-device.** Before any move the device id of every root is compared with the quarantine dir's (no-follow stat). Different → exit 3, nothing moved. There is NO copy fallback: copy-then-delete would be a delete. A rename that still fails mid-run (including a real cross-device error) stops at once with exit 3; already-moved items stay moved (journalled and evented).
- **Bounds.** The walk is read-only and completes before the first move. Leftovers are capped at `--max-items` (default 1000), entries visited at 100,000, depth at 64. Over any cap → exit 3, nothing moved, a stderr line naming the cap.
- **Names.** All path handling uses raw bytes; a non-UTF-8 name never panics and is quarantined like any other (hex bytes in the journal, the `untokenable` form in the event).

## `harness quarantine delete-listed`

```
harness quarantine delete-listed <ticket> --id <id> --manifest-dir <abs> [--ts-ms <n>]
```

Deletes exactly ONE live manifest entry of class `temp_dir`, named by `--id`. The fence is a COMPONENT WALK over the real world, never a check of the stored spelling: any `..` or `.` component is refused (the raw text is scanned — `Path` hides interior `.`); every root is re-validated as the sweep validates it (a no-follow stat, a real dir, canonicalizable, never a link); and the stored spelling must start at a canonical root's spelling (a hand-appended line with a foreign spelling is refused, fail closed). The path is then walked from that root ONE COMPONENT AT A TIME: each intermediate is examined with a no-follow stat, required to be a real directory (a parent that is a symlink — a swapped component or a symlink LOOP included — means the listed path does not resolve inside a root: exit 2, nothing deleted), and entered by a chdir that is verified against the stat by dev/ino, so a component swapped for a link between the check and the act is never followed into. The final component is examined with a no-follow stat: a symlink entry is removed as the link only (never its contents — the `node_modules` rule); a real directory is removed with the standard library's `std::fs::remove_dir_all` — the openat-based recursive delete that never follows a symlink inside the tree (a link inside, or one swapped in mid-delete, is unlinked as the link, its target untouched) and recurses with no path-length limit, so a listed temp dir deeper than the filesystem's PATH_MAX deletes cleanly instead of wedging (r2, A8). Only after the path is gone is the manifest `remove` line written — a crash between leaves a listed half-deleted thing, never an orphan; a re-run on an already-absent path just writes the remove. Any other class, an unknown or non-live id → exit 2.

Teardown (P1B-14) deletes manifested `temp_dir` entries only through this verb, never a second delete path — two delete paths drift (see [Teardown](workspace.md#teardown-p1b-14)).

**Caller rule (working directory and threads).** The component walk inside `quarantine::delete_listed` changes the process working directory while it runs (saved and restored before the function returns), and the working directory is shared by every thread in the process — so the call is now REFUSED in code, not merely forbidden by this doc (#185): `delete_listed` first proves the process is single-threaded, and stops with exit 3 (one fixed folder-free stderr line naming threads; nothing deleted, nothing written) when another thread exists or when the thread count cannot be read. P1B-14 (finalize teardown) therefore runs each delete as the `harness quarantine delete-listed` verb in its own process — single-threaded by construction — one id per call, and treats exit 3 as teardown failure, never an in-process retry.

## `harness quarantine drop-build`

```
harness quarantine drop-build <ticket> --root <abs> [--root <abs> ...] --manifest-dir <abs> --caps-dir <abs> [--dry-run]
```

Removes the cache-tagged build output of a ticket whose manifest shows it closed. The private wrapper builds a fresh gate clone of the ticket tree per gate run, moves earlier clones aside and moves the ticket's ignored build output aside at finish; this verb finds those folders under the given roots and deletes their `target` folders. The wrapper calls it at finish (a later wrapper ticket); this verb writes no event.

- **Order of steps.** Usage (option shapes, including an absolute `--manifest-dir` and `--caps-dir` with no `..`, and at most 8 `--root`); the ticket id (the sweep's token rule); the single-thread guard (the removal changes the process working directory, so the verb refuses with exit 3 in a process that holds another thread); `--manifest-dir` and `--caps-dir`; each `--root`; the per-ticket lock; the closed proof; the walk (read only, complete before the first removal); the removals. The first failing step before the removals is one stderr line and stops with nothing removed (a usage error prints its error line and the USAGE text); a failure inside the removals stops the run with what it already removed kept (see The delete). No path appears on either stream.
- **Roots.** 1 to 8 `--root` values. Each is absolute, holds no `.` or `..` component, is a real directory (a link is refused by a no-follow stat) and is canonicalized once; its canonical parent equals the canonical parent of `--manifest-dir`, so the roots sit beside the manifests folder in one state folder (a home folder, a repo clone or `/` is refused). The manifest dir and the caps dir lie inside no root. Two roots that are equal or nested are refused. A refusal about one root names its 1-based position (`--root 2`), no path; the refusals that the manifest dir or the caps dir lies inside a root name no position. Exit 2.
- **The lock.** The per-ticket caps lock (the same lock `harness ticket gate` takes, taken without waiting) is held from before the closed proof is read until the verb ends. Busy: exit 3, a run for this ticket is in progress. Any other lock error: exit 2. A ticket refused after the lock leaves an empty lock file behind.
- **The closed proof.** The ticket's manifest must read (missing or unreadable: exit 2), be clean (torn or corrupt: exit 2), hold no live entry, and hold a remove line for the id `worktree`; a miss on either of the last two says the ticket is not closed (exit 2).
- **Ticket folders.** A direct child of a root named exactly `<ticket>`, `<ticket>.old.<d>.<d>` or `<ticket>.<d>.<d>`, where `<d>` is 1 to 20 ASCII digits. A child that also matches another id under these forms, its own whole name included (`a.1.2` is also ticket `a.1.2`), is skipped when a manifest file for that id exists in the manifest dir; a stat on that file that fails any way other than NotFound stops the run (exit 3, nothing removed). A child that is a link is not followed.
- **The tag rule.** Inside a ticket folder the walk uses no-follow stats and does not enter links, entries named `.git`, or folders named `target`. A folder named `target` is a match when it is a real directory on the same device as its root and holds `CACHEDIR.TAG` — opened with no link follow and no blocking, the handle checked a regular file, at most 64 bytes read, the bytes starting with the signature line `Signature: 8a477f597d28d172789f06886806bc55` followed by a newline (the cache directory tag standard; the tag cargo writes). Anything else named `target` is kept: a link or a file is not counted, a real folder is counted in `kept`.
- **Caps.** Depth 16 below a root, 200000 entries visited, 1000 matches (the sweep's caps are its own). Over a cap: exit 3, one line naming the cap, nothing removed. A folder inside a ticket folder that cannot be read, or an entry that cannot be examined: exit 3, one line, nothing removed.
- **The delete.** Each match is reached from its canonical root one component at a time, each component entered by a chdir verified against its stat; after the last chdir the final `target` is checked again (a real directory, same device, the tag rule), and a check that fails now is kept and counted in `kept`. Inside `target`, each entry other than `CACHEDIR.TAG` is removed (a folder with `std::fs::remove_dir_all`, a file or link with `std::fs::remove_file`), then the tag, then `target` itself with `std::fs::remove_dir` from its parent reached again from the root — so a removal that stops before the tag is removed leaves the tag in place and the next run finds the folder again, while a failure after the tag is removed (re-reaching the parent or removing the emptied `target` itself) leaves an empty `target` with no tag, which later runs keep. A removal that fails part way stops the run at that match: exit 3, one line naming the count removed before it. The working directory is restored before the verb returns.
- **Output.** One line `drop-build=done ticket=<t> removed=<n> kept=<k>`; with `--dry-run` the walk runs, nothing is removed, and the line is `drop-build=dry-run ticket=<t> would_remove=<n> kept=<k>`. `removed` counts target folders removed; `kept` counts real `target` folders the walk visited and did not remove.
- **Exit codes.** `0` done (including nothing to remove); `2` refused (usage, a bad ticket id, a bad or misplaced dir or root, a damaged or not-closed manifest, a lock error other than Busy); `3` cannot proceed (another thread in the process, a held ticket lock, over a cap, a walk error, a removal that failed part way).
- **Kept.** Manifests, caps records and locks, results, logs, the ticket root with its evidence, source files, anything untagged.

## `harness quarantine put`

```
harness quarantine put <path> --quarantine-dir <abs> --manifest-dir <abs> --kind <k> --why <text> --by <token>
    [--ticket <token>] [--repo <token>] [--ts-ms <n>]
```

Moves one item (a folder or a regular file) onto the shelf in its own entry, with a label written before the move and completed after it, or refuses. Put removes nothing. `<k>` is one of `worktree`, `gate-clone`, `ignored-leftover`, `seat-old`, `findings-rejected`, `smoke-fail`, `hand`. `--why` is 1 to 200 bytes of printable ASCII with no double quote and no backslash. `--by`, `--ticket` and `--repo` are plain tokens. `--ts-ms` sets the clock; its UTC day is the entry day.

- **Order of steps.** The first failing step is one stderr line starting `harness: error:`, and no path is printed. Steps 1 to 6 write nothing, so a refusal there leaves the disk as it was: (1) usage and value shapes; (2) the two dirs; (3) the source; (4) placement; (5) the live check; (6) the device, then the walk. From step 7 on, a refusal before the move keeps the shelf folders and the lock file, and its line says nothing was moved: (7) the shelf; (8) entry, label, journal and the move. A usage error prints its error line and the USAGE text (exit 2).
- **Path spelling.** `--quarantine-dir`, `--manifest-dir` and the source are absolute, and their raw bytes hold no `.` or `..` component and do not end in `/` or `/.`. A link written `link/` or `link/.` resolves through the link, so those spellings are refused outright. The two dirs are real directories (a no-follow stat), canonicalized once, not `/`, and lie outside each other. The source exists, is not a link (the refusal line says link), is a folder or a regular file, and is not `/`. Its parent is canonicalized once. Exit 2.
- **Identity compare.** Placement is compared on the device and inode of no-follow stats, not on spelling (on a case-insensitive disk `canonicalize` does not fix the letter case of the last name). The source is refused when it equals or lies inside the quarantine dir or the manifest dir, or holds either of them. Exit 2.
- **Live check.** Each file in `--manifest-dir` whose name ends in `.jsonl` is a manifest; a stem that is not a plain token is exit 2. Other names and sub-folders are skipped. Each manifest is read with the manifest reader; one that cannot be read or is not clean is exit 2 and the line names its ticket id, because put cannot prove the source is not live work — the manifest is fixed by hand. The source is refused (exit 2) when it equals, lies inside or holds a live path entry of any manifest: on identities for an entry that exists, on canonical text for one that does not.
- **Device and walk.** The source and its parent must be on the quarantine dir's device, else exit 3 (no copy fallback). The walk is read only, uses no-follow stats, does not enter links and completes before anything is written. Caps: depth 64 below the item, 1000000 entries visited; over a cap is exit 3. A folder that cannot be read, an entry that cannot be examined, or an entry on another device than the item is exit 3. A folder named `target` that holds the cache tag (the drop-build tag rule) is not entered and has no fingerprint line; it moves with the item and the label counts it in `skipped_build`. An entry named `.git` in any ASCII letter case, at any depth outside a skipped `target`, the item itself included, is exit 2 (`the item holds a git repository that put cannot audit yet`).
- **Shelf layout.** `<quarantine-dir>/@shelf/lock`, `@shelf/entries/<YYYYMMDD>/<kind>-<n>/` holding `label.json` and `item`, and `@shelf/journal/<YYYYMMDD>-<k>.jsonl`. The sweep layout `<quarantine-dir>/<ticket>/<batch>/<item>` sits beside it; `@shelf` holds a character outside the ticket token alphabet, so the sweep does not make it. Each shelf folder is made with mode 0700 when missing and opened with no link follow; a link or a non-folder at `@shelf`, the lock file, `entries`, the day folder or `journal` is exit 2. The lock file is opened with no link follow and locked without waiting until put ends; held by another put is exit 3 (`a put is running`). `<n>` is the lowest number from 1 whose entry folder an exclusive mkdir creates (a taken name is skipped, not reused; past 10000 is exit 3). Original names are not used as entry names.
- **Label.** `label.json`, one line, fixed field order: `v`, `entry`, `kind`, `from_hex` (hex of the canonical parent, a slash and the source name, raw bytes), `src_dev`, `src_ino`, `ticket`, `repo` (empty when not given), `by`, `at_ms`, `why`, `files`, `bytes`, `skipped_build`, `fingerprint_before`, `fingerprint_after`, `state` (`intent`, `moved` or `void`), `judgeable` (`yes` or `no`), `reason` (empty or `changed-during-put`), `git` (`none`). Paths are hex only.
- **Fingerprint.** The sha256 of one line per visited entry, sorted by raw relative path bytes: `<relpath hex> <type f|d|l|o> <mode octal> <size> <inode> <ctime s>.<ctime ns> <link text hex or ->`, the item itself with the empty path. A folder writes `-` for size and ctime, the item itself writes `-` for ctime (the rename changes it); ctime is used for the other types because mtime can be set back by hand. `files` counts the item and each entry the walk visits (a skipped `target` counts once); `bytes` sums the sizes of the regular files visited.
- **Journal.** Put writes journal lines and reads none. Three line shapes, exact bytes, no spaces: `{"v":1,"op":"intent","entry":"<YYYYMMDD>/<kind>-<n>","src_dev":<n>,"src_ino":<n>,"label_sha":"<hex>"}`, `{"v":1,"op":"moved","entry":"...","label_sha":"..."}` and `{"v":1,"op":"void","entry":"...","label_sha":"..."}`. The writer appends to the file with the highest k of the entry day (made with create-new when none exists) under an exclusive lock, one write, `sync_all`. When that file does not end in a newline (a fragment left by a write that did not complete), the writer makes the next file `<YYYYMMDD>-<k+1>.jsonl` and appends there, so a fragment does not join the next line and nothing is cut or removed.
- **Write-ahead order.** All under the shelf lock: (a) the entry folder by exclusive mkdir; (b) `label.json` created with `sync_all`, state `intent`; (c) the intent line; (d) the verified parent chain of the source, the name `item` checked absent in the entry, then the rename (the sweep's `rename_verified`); (e) the item is walked again in its new place and `label.json` is replaced through `label.json.<pid>-<k>.tmp` with state `moved` and `fingerprint_after`; (f) the moved line, carrying the sha256 of the final label bytes. When the parent chain no longer matches, the source is not the one that was walked, or the rename fails, nothing was moved: the label is replaced with state `void`, a void line is written, and put ends exit 3. When the two fingerprints differ the label says `judgeable` `no` with reason `changed-during-put` and put ends exit 3. A write failure after the rename is exit 3 and the line says the item was moved and the label may still be in state `intent`.
- **Output.** One stdout line `put=done entry=<YYYYMMDD>/<kind>-<n> files=<f> bytes=<b>`, stderr empty.
- **Exit codes.** `0` done; `2` refused (usage, a bad value, a bad or misplaced dir or source, a damaged manifest or a manifest name that is not a token, a live entry, a git entry, a link or non-folder on the shelf); `3` cannot proceed (another device, a held shelf lock, over a cap, a walk error, a move that did not happen, an item that changed during the put, a write failure).

## Exit codes and output

`0` done (including zero leftovers); `2` refused (usage, bad or misplaced folders — including the event log inside a root — a root that is a symlink or outside the base, a damaged manifest, a quarantine shelf that is a link or a file, a listed path with a `..`/`.` component, one whose stored spelling does not start at a canonical root, or one whose parent chain holds a symlink — a swapped component or a symlink loop — so it does not resolve inside every root, wrong class or id); `3` cannot proceed (cross-device, over a cap, an undecidable journal intent, a leftover whose parent chain changed mid-run, a rename/journal/event write failure mid-run, a listed path or folder that cannot be examined or deleted). Success prints one stdout line of fixed fields — `quarantine=done ticket=<t> moved=<n>` / `delete=done ticket=<t> id=<id>` — and no folder path is ever printed on either stream (the workspace privacy rule, `docs/workspace.md`).

## v1 limits (honest)

- No no-replace rename syscall in std: the no-overwrite promise rests on the fresh exclusive batch dir, generated item names, and the no-follow absent check right before the rename. A same-user writer inside the fresh mode-0700 batch dir between check and rename could still race; the batch is created by this process, which bounds that to same-user code.
- The event lands after the move: a crash between the two leaves a moved item with no event until the next sweep reconciles it from the journal. A consumer reading the event log before a re-run sees one fewer event than items on the shelf; finalize (P1B-15) runs the sweep, so reconcile runs first.
- The cross-device refusal is exercised in CI through a library seam (`sweep_with_device_probe`), not a real second filesystem; the real cross-device rename error is covered fail-closed by construction (any rename error → exit 3).
- Residual check-then-act windows (r2). Delete: between the last component verification and the `remove_dir_all` call, a same-user writer can still replace components of the listed path; `remove_dir_all` never follows a link (a swapped-in link is unlinked as the link), so the worst case is deleting a different REAL directory that appeared at the listed location inside the roots — never anything outside them. Sweep: the window is CLOSED (#187) — an item's ancestor re-check opens every ancestor the walk recorded (a no-follow, non-blocking directory open: `O_DIRECTORY | O_NOFOLLOW`, so a swapped-in link, FIFO or device fails the open itself instead of being followed or blocking) and matches the handle's stat against the walk's dev/ino, and the rename names the item relative to that VERIFIED PARENT HANDLE (the destination relative to the fresh batch handle), so no source path is re-resolved at rename time and a swap landing between the re-check and the move can no longer redirect the rename: the item's real file is moved from the real directory and the file behind the swapped-in link, outside the roots, is untouched. A swap landing before the re-check skips the item (exit 3 naming the parent chain). It is a move onto the shelf (journalled, evented, recoverable), never a delete.
- Ownership in the sweep is a case-SENSITIVE lexical compare (r2, A11): on a case-insensitive disk, an entry listed as `<root>/TMPY` before it exists whose folder then appears on disk as `tmpy` is treated as a leftover and MOVED to quarantine — the safe direction (moved, never lost). `workspace create` uses fixed lowercase names and `manifest add` stores the on-disk spelling, so the standard layout never hits this.
- A listed path whose manifest line would exceed the reader's 4096-byte line cap (possible only past Linux's PATH_MAX) cannot be listed at all: the manifest fails closed at read, and no delete is reachable through it.
- The threaded-caller guard exists since #185: `delete_listed` proves the process is single-threaded before it reads anything and refuses (exit 3, nothing deleted) otherwise. The macOS reading is STICKY — any thread ever started, even one long joined, keeps the answer "threaded", so an in-process caller that ever used worker threads is refused ever after (intended: run the delete as the child verb). Linux reads the thread count from procfs; an unusual container without procfs, or any host where the count is unreadable, refuses — fail closed, never a pass. A future fd-relative walk that never changes the working directory would lift the guard; it has not been built (the current walk survived three review rounds, and a hand-written recursive delete is exactly the class review r2 caught deleting outside the roots).
- `drop-build` keeps a check-then-act window between the second check of a match and the removal of its entries (as delete-listed does): a same-user writer can swap components in that gap. The walk from the root is component by component and the second check still asks for a tagged `target` folder at that place; a swapped ancestor of the root between the walk and the removal is not detected.
- A `drop-build` removal that fails after the tag was removed (re-reaching the parent from the root, or removing the emptied `target` folder) leaves an empty `target` with no tag; later runs keep it.
- `drop-build` checks the device of the `target` folder itself; a mount deeper inside `target` is not checked.
- The three `drop-build` ticket folder name forms follow the private wrapper layout until the engine makes the gate clone itself.
- `drop-build` writes no event.
- `put` keeps the sweep's rename window between the verified parent and the rename. std has no no-replace rename, so a same-user writer inside the fresh entry folder between the mkdir and the rename could race.
- `put` writes no event; the journal line carries the label sha instead.
- An item holding `.git` is refused until the git audit ticket lands. A repository with no `.git` entry (a bare clone) is put as a plain item, and a repository inside a tagged `target` folder is not seen.
- A put stopped part way stays unsettled until the settle ticket lands; the next put skips its entry number. An entry made before its intent line reached the journal holds no item and is not settled.
- The fingerprint lines are held in memory and sorted: at the 1000000-entry cap that is several hundred MB (an estimate: hex path text plus about 80 bytes per line, and the sha256 copies its input).
